1. What problem does it solve?

Think of Gmail "Send later" plus a cold-email tool. A user writes one email, uploads a list of 5,000 addresses, and says: "Start at 9:00, send one every 2 minutes, max 200 per hour." The system must send each email at the right time, never twice, never lose one if a server crashes, and never send faster than the limits.

That is hard because servers crash, many workers run at once, and "send an email" cannot be undone. The design is about three guarantees:

1. Not lost

Postgres stores every email before anything else happens.

2. Not duplicated

Idempotency key, row claim, Redis receipt, stable Message-ID.

3. Not too fast

Redis Lua script reserves a send slot and counts hourly quota.

2. Architecture diagram

  1. 1 Browser sends POST /api/emails with sender, recipients, subject, body, start time, delay, hourly limit, idempotency key.
  2. 2 API saves campaign + all email rows in one DB transaction.
  3. 3 Only after commit, API adds one BullMQ delayed job per email. Job ID = email ID.
  4. 4 When a job is due, a worker takes it from Redis.
  5. 5 Worker claims the row in Postgres (compare-and-set) and later writes SENT.
  6. 6 Worker asks a Redis Lua script: "which slot may I send in, is quota left?" Writes receipt after SMTP.
  7. 7 Worker sends via Ethereal SMTP.
  8. 8 If a limit is hit, worker posts to Slack (once per hour per scope).
  9. 9 Worker queues a search-sync job; another worker bulk-indexes into Elasticsearch.

3. Life of one email (step by step)

A. Schedule (API)

  1. Zod validates. Max 5,000 recipients, body ≤ 100 KB.
  2. Body is HTML-sanitized.
  3. buildSchedulePlan: lowercases + de-dupes recipients; email i gets start + i × delay. Hash of payload saved.
  4. Same idempotency key + same hash → return old campaign (200). Different hash → 409.
  5. Transaction: create sender (ON CONFLICT DO NOTHING), campaign (body and preview stored once), N slim email rows, N search-outbox rows.
  6. After commit: addBulk jobs in chunks of 500 with delay = scheduledAt - now, only for emails due within the queue horizon (6 h). Later emails wait in Postgres; the reconciler queues them in time.
  7. Queue search-sync job and clear the outbox rows (if Redis is down, the outbox keeps them). Return 202.

B. Deliver (worker)

  1. Load row. If already terminal, stop.
  2. Receipt check. Redis key says SMTP already accepted? Just mark SENT.
  3. Suppression check. Recipient unsubscribed, complained, or bounced? Mark CANCELLED. No quota, no SMTP.
  4. Reserve slot (Lua): slot = max(now, lastSlot + 2s). Count sender, campaign, tenant quota for the hour of that slot. Full → move job to next hour + jitter and ping Slack.
  5. Sleep (BullMQ moveToDelayed) until slot.
  6. Start guard (Lua): real starts of one sender ≥ 2 s apart.
  7. Claim: UPDATE ... SET PROCESSING WHERE SCHEDULED (or stale lease). One winner.
  8. Send with stable Message-ID: <emailId@reachinbox.local>, through the sender's own SMTP login if it has one. Unsubscribe link and header included.
  9. Write Redis receipt, then Postgres SENT, publish SSE event, queue search sync.
  10. Temporary SMTP error → back to SCHEDULED, BullMQ retries (5x exponential), then FAILED. Permanent error (5xx) → FAILED at once; 550/551/553/554 also suppress the address.

C. Restart survival

Jobs live in Redis (AOF every second) and as rows in Postgres. On boot, and every 5 min, one process (leader lock) scans all SCHEDULED rows. Any row with no live job gets a new job with the same ID. Any PROCESSING row older than the 5 min lease goes back to SCHEDULED; on its next claim it is marked FAILED (“outcome unknown”), never resent. Even if Redis is wiped, no email is lost.

This is setInterval, not cron. Scheduling itself is BullMQ delayed jobs. The reconciler is only a safety net. Say that clearly in the demo.

4. Why each decision was made

Decision Why Trade-off
Postgres is truth, Redis is an index (ADR 0001) Redis can lose ~1 s of writes or be flushed. A DB row cannot be "forgotten". Two stores to keep in sync, so a reconciler is needed.
Commit rows before publishing jobs Crash between the two is repairable. The reverse order could send an email with no record. Brief window where a row has no job (reconciler/retry fixes).
Job ID = email ID Publishing twice is a no-op. Makes every retry safe. None meaningful.
Client idempotency key + payload hash Double-click or network retry never makes a second campaign. Client must generate keys.
Reserve send slots in Lua (ADR 0002) Old design: poll "can I send?" → O(n²) wakeups for 5,000 due emails, and BullMQ's global limiter capped the whole system. Reservation = one atomic call, job sleeps till its slot. Cancelled and known-failed sends refund quota. Redis is on the hot path.
Quota charged to hour of the slot Hour boundary can't let one hour exceed the cap. Now a sliding window (Redis sorted sets).
15-minute look-ahead horizon A cancelled campaign cannot hold slots hours into the future. Jobs far back wake every ~15 min.
Over-limit → next hour, not fail Brief says never drop or fail. Jitter (up to 60 s) avoids a thundering herd. Order within the hour is approximate.
Claim via compare-and-set + lease Two workers can't both own an email. Dead worker's lease expires; the email is then failed, not resent. Lease length = recovery delay.
Receipt in Redis before DB (ADR 0003) SMTP has no idempotency. If DB fails after sending, retry sees receipt and doesn't resend. Crash mid-send is failed, not resent (at-most-once after claim).
Search is async projection (ADR 0004) ES slow/down must not block sending or the API. External version = updatedAt stops stale overwrites. Search lags seconds. Lists come from Postgres.
Separate API and Worker processes Scale and restart independently. Graceful shutdown waits for in-flight sends. More processes to run.
SSE (not websockets) One-way live status. Simple. One Redis subscriber per API process. Connection count per node is limited.
Signed cookie JWT + Redis deny-list Stateless API replicas; logout still revokes immediately. Redis read on each request.
AES-GCM for Slack tokens Secrets not readable from a DB dump. Key in env (not KMS).

5. What happens when things crash

Event Result Risk
API dies before DB commit Nothing saved. Client retries with same key. none
API dies after commit, before jobs Reconciler (or client retry) adds jobs. none
Redis restarts / is wiped AOF restores; else reconciler rebuilds jobs and the hourly quota sets from Postgres (emails sent in the last hour). reserved slots re-reserved
Worker dies before SMTP BullMQ stall detection (30 s) re-runs. none
Worker dies after SMTP, before receipt Claim marker stays in Postgres. Next attempt marks the row FAILED ("outcome unknown"). Never re-sent. one manual resend
Postgres fails after SMTP Receipt exists; retry only marks SENT. none
Two workers get same email CAS: one wins; other waits for lease. none
Elasticsearch down Sync retries 8x; /health says degraded; sending continues. stale search
Slack down / not connected No crash, no alert, delivery continues. alert only

6. Would it handle 1,000,000 users?

No, not as built. It is correct and well reasoned, but it has one Postgres, one Redis, and one ES node. The reconciler is now bounded by the queue horizon and senders can have their own SMTP login (section 7), but sharding is still future work.

Assumptions (say them out loud)

1M registered users. 10% active a day. Each active user schedules 500 emails/day ⇒ 50M emails/day ≈ 580/s average, ~5k/s at peak. The repo's own load test: ~250/s on a laptop with 4 workers and a stub transport. With real SMTP, each sender is capped by MIN_SEND_INTERVAL_MS (2 s → 0.5/s) and 200/h.

What breaks first, in order

# Bottleneck Why Fix
1 Reconciler scan bounded now Used to read every SCHEDULED row. It now reads only rows due inside the queue horizon, so cost follows the horizon, not the backlog. Done: (status, scheduledAt) index and horizon. Next step at 1M users: a dispatcher with SKIP LOCKED (see #2).
2 One BullMQ job per email in one Redis horizon now Used to be 50M delayed jobs × ~1 KB. Now only emails due in the next 6 h own a job. At 5k/s peak that is still a lot of Redis memory, so a dispatcher is the next step. Just-in-time dispatch: emails live only in Postgres. A dispatcher pulls rows due in the next ~1 min with FOR UPDATE SKIP LOCKED and enqueues only those.
3 Single Postgres The body is now stored once per campaign (was up to 500 MB per campaign). Still one primary. groupBy stats scan per user. Partition email. PgBouncer. Read replicas. Cached counters.
4 Attachments in Postgres Bytes Workers now cache them per campaign (LRU), so the DB is read once per campaign per worker, not per email. Bytes still live in Postgres. Object storage.
5 Single Redis for everything Queues, Lua counters, rate limits, receipts, pub/sub share one CPU thread. Shard Redis by tenant (Lua already uses a {tenantId} hash tag). Split pub/sub and HTTP limits out.
6 SMTP identity and reputation Senders can now have their own login, and unsubscribe, complaint and bounce handling exist. No DKIM/SPF or warm-up; Ethereal sends no async bounces. SES/SendGrid. Provider bounce + complaint webhooks into /api/suppressions.
7 SSE on API nodes Each node holds sockets; every event is fanned to every node's pattern subscriber. Missed events replay after a reconnect (last 500, 1 h). Dedicated realtime gateway.
8 Elasticsearch single node Indexes full body of every email. Security is on; outbox keeps it fed. Multi-node cluster, ILM, Kafka behind the outbox.
9 Noisy neighbour One tenant's 5,000 jobs share queue and workers with everyone. Per-tenant queues, weighted fair scheduling.

Target design for 1M users

  1. Schedule: API writes campaign (body once) + slim recipient rows + outbox event. No Redis call at request time.
  2. Dispatch: dispatchers claim rows due soon (SKIP LOCKED) and push to per-tenant queues. Redis stays small. Restart safety comes from Postgres being the only schedule.
  3. Admit: keep the Lua slot-reservation idea (good and cluster-safe). Quotas are already a sliding window; add tenant-level token buckets.
  4. Send: per-sender SMTP creds or provider; bounce/complaint handling stops bad sends.
  5. Project: search and live updates fed from the DB outbox via Kafka, not request paths.
  6. Operate: autoscale workers on "oldest ready job age" (metric already exists), multi-AZ, per-tenant fairness.

Most current ideas survive: Postgres as truth, idempotent job IDs, CAS claim, receipts, Lua reservation, async search. The change is where the schedule lives (Postgres, not millions of Redis delayed jobs) and sharding.

7. Flaws and gaps (all 11 fixed)

Each flaw from the earlier audit now has a fix in the repo, a test, and a trade-off. Per your project rules, this is assignment-scope work, not production hardening. Fixed means the code changed and is covered by the unit or integration suite.

Sev Flaw Status Fix and where
HIGH Reconciler is O(all scheduled rows) FIXED services/recovery.ts reads only rows due inside the queue horizon, using the new (status, scheduledAt) index. Cost follows the horizon, not the backlog. Unit test checks the query. ADR 0005.
HIGH One BullMQ delayed job per email FIXED queues/emailQueue.ts: only emails due within ENQUEUE_HORIZON_MS (default 6 h) get a job. Later ones stay in Postgres and the reconciler queues them when they come into range. Integration test: a week-out email has no job until then. Trade-off: queueing lags by up to one tick.
HIGH "Multiple senders" share one SMTP login FIXED services/transports.ts, routes/senders.ts: a sender can have its own SMTP login (encrypted at rest, own pooled connection). Without one it uses the shared account. Ethereal is still a fake inbox, so this proves the wiring.
MED Body copied into every email row FIXED Body is stored once on the campaign; lists read a stored Campaign.preview. Migration moved existing bodies up and cleared the row copies. Integration tests check null row bodies, the preview, and the detail route.
MED Attachments in Postgres, reloaded per send FIXED services/attachmentCache.ts: per-worker LRU, bounded by ATTACHMENT_CACHE_BYTES. A campaign reads its files once, not once per recipient. Bytes still live in Postgres (no object storage).
MED No bounce / complaint / unsubscribe handling FIXED Suppression list, signed unsubscribe link with List-Unsubscribe headers, complaint endpoint, and SMTP 5xx handling (no retry; 550/551/553/554 suppress the address). The worker skips suppressed recipients before quota is charged. ADR 0006. Ethereal sends no async bounce emails, so only synchronous rejections are handled.
LOW Reconciler timer lives in API only FIXED startReconcileLoop() runs in both the API and the worker. The leader lock keeps it single.
LOW Encryption key falls back to SESSION_SECRET FIXED DATA_ENCRYPTION_KEY is required. Rotation: DATA_ENCRYPTION_KEY_PREVIOUS plus pnpm rotate-secrets. Unit test covers rotation and no silent fallback. Still no KMS.
LOW ES: no security, single node FIXED docker-compose turns Elasticsearch security on (user elastic); the API signs in with ELASTICSEARCH_USERNAME/PASSWORD. Verified: no-auth request gets 401. Still a single node, which is fine for the demo.
LOW SSE per node, no replay FIXED events/publisher.ts, events/stream.ts: every event goes to a capped per-user Redis stream and carries an SSE id. A reconnect with Last-Event-ID replays what was missed; a trimmed log sends resync. Integration test covers the replay. Each node still has its own sockets.
LOW Search can miss docs FIXED Search outbox in Postgres, written in the schedule transaction and drained by the reconciler if Redis was down. ADR 0007. pnpm reindex remains for other drift.

9. Likely interview questions, short answers

Why not cron?

Brief forbids it. BullMQ stores the run time in Redis; workers wake when due. The reconciler uses setInterval only to repair gaps.

How do you avoid duplicates?

Four layers: idempotency key at API, job ID = email ID, CAS claim in Postgres, Redis receipt after SMTP. SMTP cannot be exactly-once; say so.

What if Redis dies?

Schedules are in Postgres. Reconciler recreates jobs. Hourly quota sets are rebuilt from Postgres sent rows.

Why Lua?

Read-check-increment must be atomic across many workers. A Lua script runs as one step in Redis.

Why reserve slots, not retry?

5,000 due emails: retry = every job wakes every 2 s. Reserve = each job gets its time once and sleeps.

What if the limit is hit?

Job moves to next hour (+ up to 60 s jitter). Never fails, never dropped. Slack alert once per hour per scope.

1000 emails at once?

All become jobs. Reservation spreads them 2 s apart per sender, capped 200/hour; the rest roll to later hours. 8 workers run in parallel safely.

Slack not connected?

Lookup finds no connection and returns. No crash. Connect later and it works with no redeploy.

Does it scale to 1M?

Not as is. Keep the schedule only in Postgres with a dispatcher, shard Redis and Postgres, use object storage, real SMTP per sender, outbox + Kafka for search. Core ideas stay.
